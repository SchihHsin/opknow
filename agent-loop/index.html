模型、运行系统与环境各做什么

Loop 不是模型单方面连续思考，而是运行系统执行模型请求并维护状态。

M
模型根据上下文生成判断、工具请求或候选答案。
R
运行系统检查请求、执行工具、追加结果、路由 Agent 并处理运行限制。
E
执行环境读取文件、访问网络、计算或修改，再返回真实观察结果。
S
状态与验证记录已完成事项、证据、失败尝试和剩余问题，独立判断是否达标。
Agent-as-Tool：专家有自己的内部循环，但任务控制权回到主 Agent 汇总。Handoff：活动 Agent 改为接收者，不默认回到 A。

04 / Design choices

任务组织模式与执行机制是两条轴

模式说明任务怎样组织；机制说明下一轮由什么控制信号触发。它们可以组合，不应该混成一个互斥分类。

组织模式 01

反馈驱动

根据当前观察决定下一步。适合信息不足、路径未知的探索任务。

组织模式 02

计划驱动

维护阶段、依赖与进度；假设失效或停滞时需要重规划。

组织模式 03

流程约束

用显式节点与条件限制合法路径，便于审计和权限管理。

组织模式 04

验证修复

按测试、规则或外部证据检查产出，并针对失败项迭代。

组织模式 05

多 Agent 协作

拆分相对独立的职责，再协调和整合结果；角色变多不保证质量更高。

八种执行机制

按下一轮触发信号理解具体实现。一个任务可以组合多种机制，例如主 Agent 使用工具循环、图路由负责验收、账本负责长任务重规划。

01Tool Calling Loop

模型发出工具请求，运行系统执行并回写结果后继续调用模型。

02Handoff Loop

当前 Agent 发起交接，运行系统切换活动 Agent；需要明确目的地和交接上下文。

03Agent as Tool

主 Agent 调用有边界的专家任务；专家返回，主 Agent 恢复并汇总。

04Conditional Graph

状态和条件函数选择后续节点，回边构成循环，END 或人工节点处理出口。

05Explicit Iteration

框架按固定顺序重复一组子步骤；需要明确退出信号和最大迭代数。

06Speaker Selection

团队调度器根据共享上下文选择下一位执行者，而非当前 Agent 自行交接。

07Ledger-driven Nested Loop

内层根据进度分配子任务；停滞检测触发外层更新计划。

08Programmatic Workflow

用程序条件、循环、并行和恢复逻辑编排步骤；副作用需要幂等或检查点设计。

边界：这是固定修复步骤与条件路由的程序化复现，真实执行了导出和验证，模型调用数为 0。它展示反馈闭环，不衡量大模型自主修复能力。
