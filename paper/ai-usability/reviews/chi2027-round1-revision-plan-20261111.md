- [ ] 将观察拆开表述：实际检索／抓取返回了什么、原始文档能支持什么、Agent 如何搜索和总结、作者据此作了什么判断。对关键 D 案例复核原始页面与摘要器输出的差异。
- [ ] 说明中文查询和搜索地区可能影响排名及第三方来源；交代任务要求的制定、生态任务配对和验证方法，标出任务范围不完全一致之处。
- [ ] 删去无足够样本支撑的生态系统普遍排名和「调试差距最大」式确定性结论；如保留分组比较，说明分组形成时间、依据、每组任务数及组内变异。
- [ ] 报告 M5、M8 与 Agent 查询和停止决策的关系；区分工具限制、研究协议和模型行为，不把其结果全部归因于生态。
- [ ] 结论限定为所测配置、任务和证据；不能把综合分写成正确率，也不能声称框架已经过全面效度验证。
- [ ] 如将三模型重跑纳入修改稿，明确它是投稿之后新增的数据，报告完整运行与缺失情况、模型和检索条件差异；它可以展示跨模型情况，但不能证明模型间独立重复、真实开发成功率或生态系统的普遍排序。

**完成标准：** 每个主要结论都能指回分析表、具体任务或案例；结论范围与观测条件一致，空值与证据局限得到说明。

## 6. AC 要求四：概念定位与 HCI 贡献

- [ ] 制作简洁对照表，比较信息检索、文档可用性、Agent 评测与本文知识可用性：分析单位、所看维度、主要输出和本文额外的任务级诊断区分。
- [ ] 用一个完整案例说明：相同的最终答案或检索成功，可能对应不同的知识来源、获取障碍、版本判定或证据充分性；明确实例来自哪些记录。
- [ ] 将 M1–M10 分类说明：主要反映知识源、Agent／工具、二者互动，或对最终回答的判断；对混合性质不强行归入单一类别。
- [ ] 将方法定位为**探索性诊断框架**，清楚区分提出方法、案例演示、可靠性核查与未来效度验证；补充实践者如何使用诊断结果的潜在场景。
- [ ] 明确设计图是概念示例；开发者决策改善、文档团队效率提升等尚未被本研究直接测量。提出后续与开发者或文档维护者共同评估的具体方法和可观察结果。
- [ ] AC 已说明在结论适当收敛时，从业者评估不是本轮必需条件。若具备时间和参与者，可以补做；无论是否开展，都要逐条回应 R2 对实际效用的关切，不能把未来计划写成已验证成效。

**完成标准：** 读者能理解该框架比单独的检索或回答正确性评测多提供哪些诊断，并清楚当前证据支持到哪一步。

## 8. 参考文献与材料

- Lawrance et al. (2013), *How Programmers Debug, Revisited: An Information Foraging Theory Perspective*：程序员信息觅食和调试。
- Wang et al. (2025), *How and Why LLMs Use Deprecated APIs in Code Completion? An Empirical Study*：API 演化与 LLM 生成代码中的版本问题。

- Howard (2024), [The /llms.txt file](https://llmstxt.org/)：与面向 Agent 的文档输出建议比较。
