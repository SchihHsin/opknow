# AI 能找到开发者所需的知识吗？开发者生态中面向 AI 的知识可得性的定义与度量

> **全量重跑修订稿：** 本副本依据实验提交87e04c1更新指标细则、实验设置与结果。156次采集和双阶段评分完成，证据未知状态保留；原审阅页不变。

## 摘要

开发者日益广泛地使用AI Agent开展软件开发，从检索技术资料、生成和修改代码，到调用工具执行任务。Agent协助开发者完成这些任务，需要能够取得可用的技术知识。本文将这些条件概念化为面向AI的知识可得性，提出任务级协议及十一项指标，涵盖知识来源、获取成本和回答属性。该方法应用于26类面向AI加速计算的软件开发任务，主比较涵盖25对CANN/CUDA任务，另单列迁移类比。结果区分了版本关系尚未取得、部分操作正文可读但关键环节不足，以及通过不同来源或路径获得补充支撑等情形；部分平均差异跨模型重复，场景顺序与来源互补则存在差异。这些发现将开发者评估技术建议所需的信息与知识缺口联系起来，为技术知识供给及Agent对知识的获取与使用等方面的改进提供方向。本文贡献一个概念框架、一套可检查的协议及其案例应用，用于诊断Agent协助开发者完成任务时所依赖的知识条件。

## 关键词

面向 AI 的知识可得性；开发者生态；技术文档；信息寻径；AI Agent；测量方法

## 引言

在传统的软件开发方式下，开发者常常需要自行查阅文档、代码示例、搜索结果和社区解释，以决定下一步行动。关于机会式编程和开发者信息需求的研究表明，寻找与解释信息本身就是编程活动的一部分 [@brand2009; @ko2007; @sillito2008]。有用的信息必须契合当前任务：命令需要正确的选项，API 示例需要对应的版本，错误解释需要提供足够的上下文来指导排查。因此，文档的存在只是其有用性的一个条件。

具备检索与工具调用能力的开发 Agent 为这一知识环境增加了一条协作路径。近期对GitHub项目的研究发现，编程Agent的采用已涉及不同成熟度和技术类型的项目 [@robbes2026]。开发者既可以围绕报错或局部代码提出问题，也可以描述待完成的变更或结果目标，将资料查找、文档阅读、实现步骤组织以及部分代码修改委派给 Agent。为推进任务，Agent 可能自行在官网、文档、仓库与社区之间搜索、读取和整合材料，再起草回答、实现方案或代码改动。关于代码生成工具、对话式编程辅助和 Agent 支持的研究既描述了这种支持带来的机会，也揭示了理解和核验生成建议的困难 [@vaithilingam2022; @barke2023; @programmerAssistant2023]。委托检索改变了支撑材料到达开发者的方式，但开发者仍需判断建议是否有可辨认的依据、是否符合本地环境，以及是否需要更多信息。Agent能否取得技术材料，是这些依据能否被呈现和检查的条件之一。测量这一获取过程，因而可以识别经由AI形成的指导所依赖的知识缺口。

Agent通常能够对开发问题给出回答，但回答是否准确、能否用于当前任务，受到其所取得知识的影响。例如，实现自定义算子时，Agent可能找到官方指南，却未能取得操作正文；排查错误时，也可能读到完整页面，但其中只有笼统的查看日志建议。在这些情况下，Agent仍可能依靠已有知识或推断继续作答，却缺少支撑具体步骤的外部依据。即使取得了详细说明，资料中的工具包与框架版本不兼容，也可能导致建议不适用。因此，评价不仅需要检查Agent给出了怎样的回答，还需要识别其知识依据缺在哪里，从而为资料完善和Agent反馈设计提供具体的改进方向。

开发者生态的建设者不仅需要知道Agent能否给出可用的技术指导，还需要判断哪些知识条件限制了这种指导，以及应当在哪里改进。相似的回答不足可能来自不同原因：官方资料未被发现、操作正文未能取得、已取得内容缺少任务细节，或版本选择依据不明确；可用的回答也可能依赖替代来源，从而掩盖官方资料的缺口。仅观察最终回答或任务结果，难以区分这些情况。本文以开发者任务的知识需求为参照，比较不同生态对各类开发活动提供的知识支撑，并结合来源、获取事件和实际内容，识别资料供给、信息组织及来源互补方面的问题，为生态建设与Agent交互的改进提供依据。

**研究缺口与本文的增量。** 现有研究分别讨论开发者如何寻找信息、文档如何支持API学习、检索增强系统是否取得相关上下文，以及Agent是否完成任务；这些工作提供了重要的概念和结果指标，但通常没有把“发现了什么、实际取得了什么、哪些任务需求得到支持、版本关系是否足以定版，以及最终回答还需怎样修正”放在同一条可追溯的证据链中。尤其是，检索结果、页面返回形态、来源归属和回答属性往往分别报告，因而难以判断问题究竟来自入口、正文交付、内容缺口、来源冲突还是回答组织。本文的额外贡献不是再提出一个答案正确率，而是提出面向AI的知识可得性构念，把上述条件按任务连接起来，并用冻结问句、实际工具返回、检索前回答和最终答案保存可复核证据。随后以CANN/CUDA案例检验这套诊断框架能否定位文档和Agent需要改进的环节；生态间差异是案例中的诊断输出，不是本文的唯一目标或总体排名。

我们将**面向 AI 的知识可得性**定义为：在明确的检索条件下，一个指定的 Agent 及工具配置能够发现、取得任务相关技术知识，并评估其适用性的程度。这是一个关系性构念：它涉及特定时点上的任务、知识环境，以及访问该环境的方式。我们通过证据记录协议和十一项指标将其操作化。这些指标区分来源条件、获取成本、回答检查，以及由 M1–M8 计算的综合置信度。

该方法的预期使用者包括产品经理、设计师、技术写作者和开发工程师等，他们参与开发者平台、技术知识资源或AI Agent的建设与维护。该方法旨在帮助他们定位技术资料在发现、获取和任务支撑方面的缺口，并明确知识供给与Agent反馈需要改进的环节。案例应用展示了可服务于这些用途的诊断区别；其在团队工作中的实际价值仍需评价。

本文提出两个研究问题。**RQ1：** 如何定义并操作化面向 AI 的知识可得性，使任务特定的访问条件与证据缺口能够被系统记录和复核？**RQ2：** 该方法在不同开发任务中揭示了哪些知识可得性模式，这些模式如何为文档与 Agent 设计提供依据？

我们通过一个方法框架及其在面向AI加速计算的软件开发任务中的应用来回答这些问题。案例覆盖26类任务，其中25类比较CANN与CUDA开发情境，一类迁移任务以ROCm/HIP为对照目的地，单独处理。案例应用将任务级测量连接到跨任务模式与设计启示。具体贡献包括：（1）一个将知识条件与检索成功、答案正确性区分开的构念；（2）一套任务级协议、指标定义和可移植的分析材料；（3）具体案例与跨任务综合分析，区分不同断点，并将其连接到文档与Agent设计。

## 相关研究与构念边界

### 开发者信息寻找与文档

信息寻径理论将信息寻找行为与可用信息的结构和预期价值联系起来 [@pirolli1999]。编程研究展示了开发者如何交织进行搜索、学习和实现，以及他们的问题如何依赖于正在开展的工作 [@brand2009; @ko2007; @sillito2008]。API 学习中的困难也促使研究者关注技术接口周围的解释性资源 [@robillard2009]。Uddin与Robillard进一步指出，歧义、内容不完整与错误是API文档中的严重问题 [@uddin2015]；Aghajani等通过分析邮件列表、Stack Overflow讨论、问题单和拉取请求，形成了文档问题的分类 [@aghajani2019]。Treude与Robillard则展示了从Stack Overflow提取API文档未包含的有用信息，以补充正式文档的可能性 [@treude2016]。Maalej与Robillard进一步对API参考文档中的知识类型进行了分类 [@maalej2013]。这些研究表明，开发者需要什么信息，与正在完成的任务密切相关。因此，本文以具体开发任务为单位，考察Agent能否找到并取得所需资料，以及资料是否提供了完成任务所需的解释、参数说明和操作步骤。

本文方法不从机器访问情况推断人类可用性。对视障开发者的研究也表明，AI编程辅助的收益可能伴随建议过多和上下文切换等无障碍问题，用户体验仍需在具体使用情境中考察 [@flores2025]。浏览器能够读取的页面可能对某个特定抽取工具不可访问；反过来，Agent 容易抽取的文本也可能让人难以导航。我们考察的是受委托的知识获取路径所面对的条件。关于开发者时间、信任、满意度或任务完成情况的主张，需要另外的证据。

### 面向编程的 AI 支持

AI编程辅助研究区分了获得建议与理解、调整和检查建议。Vaithilingam等描述了理解、修改和调试生成代码时的困难 [@vaithilingam2022]；Barke等区分了开发者使用代码生成模型时的加速与探索模式 [@barke2023]；Ross等考察了围绕代码上下文开展的对话式辅助 [@programmerAssistant2023]。Liang等对410名开发者的调查发现，输出难以满足功能或非功能需求、难以控制生成结果，是重要的使用障碍 [@liang2024]。Mozannar等通过开发者活动分类分析与代码建议交互的行为和时间成本，说明评价也需要关注建议生成之后的使用过程 [@mozannar2024]。在安全相关编程任务中，Perry等发现，使用AI辅助的参与者编写了更不安全的代码，却更可能认为自己的代码是安全的，提示主观信心与实际质量需要分别检验 [@perry2023]。这些发现促使我们关注开发者考虑一项建议时能够获得哪些支撑信息。本文协议检查相关来源段落、版本条件和操作细节能否被取得并与建议关联，为研究开发者如何使用AI辅助提供知识条件层面的描述。

Agent 能够交织推理与工具使用，而检索增强生成提供了将外部信息纳入生成过程的方式 [@lewis2020; @yao2023]。WebArena、SWE-bench 和 SWE-agent 在贴近真实的网页与软件工程情境中评估或开发 Agent [@zhou2024webarena; @jimenez2024swebench; @yang2024sweagent]。其任务结果是系统表现的重要证据。本文框架则对这些系统运行时面对的知识条件提供互补描述。失败可能涉及证据不可得、对可得证据的解释不充分，或执行不成功；本文方法直接处理其中第一类问题，并记录有助于区分这些情形的信息。

### 检索、归因与可得性构念

现有研究从多个层面评价AI系统。ALCE关注生成答案的流畅性、正确性和引用质量；RAGAs与ARES进一步评价检索上下文的相关性，以及答案对上下文的忠实程度 [@gao2023alce; @ragas2024; @ares2024]。AgentBoard通过细粒度任务进展率等指标分析Agent的行动过程，说明最终成功率之外的过程信息也具有评价价值 [@ma2024agentboard]。在编程情境中，RepoBench分别评价跨文件代码检索、代码补全及二者组合的流程，明确区分了上下文获取与生成表现 [@liu2024repobench]。其对象是代码仓库中的补全任务；本文则检查开发任务所需的官方与第三方技术资料能否被发现、取得并提供充分支撑。这些方法为理解系统表现提供了基础。对于开发者生态的建设与维护，还需要将表现与具体知识条件联系起来：相关技术资料是否容易发现，所需正文是否实际取得，内容是否提供操作所需的细节，以及版本之间是否存在明确的选择与配套依据。本文围绕这些关系组织任务级测量，以区分需要改善获取路径、完善资料内容或明确版本关系的情形。

## 方法框架

### 分析单位与任务需求

分析单位是一次**任务侧知识获取过程**：使用明确的 Agent 和检索配置，在特定技术生态中围绕一个开发目标开展知识获取。任务说明记录期望结果、初始材料、约束、版本依赖，以及支撑下一步行动所需的证据。例如，模型转换可能需要转换命令、输入形状说明、目标设备设置，以及检查生成产物的方法。这些需求指导检查；页面长并不自动意味着内容充分。

任务选择与抽样应得到明确说明，并服务于评价目的 [@kelly2009]。生态评估可能寻求覆盖不同工作流；文档团队的审计可能聚焦反复出现的支持问题。若无进一步的抽样证据，两者都不能说明这些任务在总体中的发生频率。跨生态应用时，分析者应记录初始条件与任务范围的差异，而不是假设名称相近就意味着任务等价。该框架也可用于同一生态内部、不同版本之间或不同检索配置之间，只要比较条件得到明确说明。

图 1 将各项测量放在一条可观察的工具调用循环中。它是一个分析模型，而非对模型隐含推理过程的重建：Agent 先搜索候选来源、选择 URL、读取正文或记录失败，再汇总证据并检查任务充分性与版本适用性。证据不足而仍有可检索空间时，循环回到查询精化；模型先验作为独立分支登记；当前协议还在检索前冻结无工具答案以供M7核查。因此，先验知识不自动视为可追溯证据。

### 知识来源与任务支撑

该框架考察三类知识来源：官方资料、第三方资料和模型自带知识。官方资料与第三方资料的区别依据发布者身份确定。例如，厂商发布的文档、代码仓库和博客属于官方资料，独立作者提供的教程与实践经验属于第三方资料；托管平台本身不决定来源归属。

对官方和第三方资料，框架考察Agent能否找到相关来源、能否实际取得内容，以及取得的内容能否支撑当前任务。具体检查包括：是否包含所需的操作步骤、参数解释或诊断信息，是否明确适用版本及组件配套关系。对于模型自带知识，当前协议在检索前冻结无工具回答，再检查其正确性与任务覆盖，并与实际取得的外部资料分别呈现。

将三类来源结合起来，可以分析任务所需知识由哪些来源提供、哪些需求仍缺少支撑，以及不同来源能否相互补充。例如，官方正文未能取得时，第三方资料是否提供了可用的操作说明；多个来源都有相关内容时，其版本与配套信息是否一致。获取次数与失败尝试则用于描述取得这些知识所需的成本。

### 证据记录

证据记录将每项判断与其依据联系起来。最低限度的字段包括任务问句与初始条件、已知的 Agent 与工具配置、采集时间、查询和选定 URL、发布者与来源角色、返回内容或相关片段、访问结果、适用版本、内容所支持的任务需求、获取次数，以及编码决定及其理由。另设字段标明条目属于直接记录、后续编码、估计，还是不可获得。

这一区分可以避免一种常见的报告错误：仅仅因为脚本为某个解释赋予了数字，就把解释转化为观测。抽取失败反映工具与来源交互的结果；将某段解释判为充分，是对照任务需求作出的判断；估计模型对某个工具包的熟悉程度，则属于推断，除非有单独测试为其提供支持。数值编码不会消除这些差别。

## 操作化与测量协议

### 十一项指标及其证据角色

本方法保留官方资料、第三方资料和模型自带知识三类来源，以及发现、获取、内容支撑、版本条件、成本与回答属性的评价目的。当前操作化采用本批冻结的`three-model-pilot-20260921+execution-checks`量规；名称沿用规则版本，不表示本次只有试跑。批次协议为`full-rerun-protocol-20260921`，评分以冻结的rules.md和execution-checks.md为准，不用当前安装Skill的默认规则替代。表2区分每项指标的评价对象。

#### 指标选择逻辑与相互关系

11项指标不是互相独立的“分数清单”，而是从任务知识链条逐层拆出：官方渠道由M1–M4覆盖发现、实际取得、内容详尽度和版本适用关系；第三方渠道由M5–M6覆盖来源数量与关键说法的证据质量；模型先验由M7单独记录；M8记录取得这些材料的检索成本；M9–M10检查外部知识进入最终回答后的版本定版与操作补改；M11只把M1–M8透明地汇总为一个连续指数。这样安排是为了让每个分数对应一种可修复的缺口，而不是重复测量同一件事。

指标之间的边界也预先固定。M1问“能否找到官方来源”，M2问“工具实际返回了多少可识别正文”；M3问正文是否覆盖任务内容，M4问资料是否给出必要的版本—组件关系；M5是相关独立第三方来源的数量，M6是关键说法能否被支持或反驳；M7不使用本轮检索内容，M8只数实际派发调用；M9和M10只看最终答案，分别对应定版和操作补改。因此，正文很长不自动提高M3，来源很多不自动提高M6，官方资料清楚也不自动提高M9。本文没有把人类导航易用性、开发者满意度/信任、端到端硬件执行成功率、延迟或token成本并入这11项，因为这些问题需要不同的观察单位和独立证据；遗漏它们是构念边界，而不是暗示它们不重要。

### 协议的应用

**第一，固定任务和条件。** 每个分析单元由任务、生态、实际请求模型、轮次及run_id标识。预先保存两侧问句、初始条件、需求清单、版本选择范围与需定版的组件，记录模型及工具身份、查询深度、搜索／获取预算、时间与停止条件。任务配对只能说明共同开发意图，不能保证难度严格相同。工具未暴露的参数标记未知。

**第二，冻结检索前回答并记录获取。** 模型在接触本轮搜索结果前完成同题无工具回答，供M7后评。随后由客户端保存真实工具请求与返回，包含每轮查询及全部有序结果、未打开或重复条目、URL、标题、摘要、位置与可得日期。获取前明确目标为完整文档或具体章节，不得事后缩小成恰好返回的片段。保留原始资源格式、工具返回表示、正文或错误信息；没有正文不能单独证明SPA、robots或动态渲染是原因。

**第三，关联需求、来源与最终回答。** 记录原始障碍、后续替代路径、恢复状态与最终仍未满足的需求。取得其他正文不能删除早期失败，也不能自动证明任务已解决。M3/M4依据实际取得的官方资料；M9/M10依据实际最终答案，引用来源段落不能代替答案原文。

**第四，分层后评并保留修订。** 每次运行保存`process.jsonl`与`evaluation.json`；自动后评原件、复核后的派生评价和事后参照另存并关联，不互相覆盖。分数须附事件编号、可定位引文和判断理由；引文匹配仅证明文字位置，不证明技术正确性。事后取得的同URL参照可用于审计运行时返回的完整性，但必须标记时间和用途，不能加入模型当时的知识上下文。

**第五，报告分数及不可评分状态。** 能判定档位时给点值，有明确上下界但不能定档时保留证据区间及原因；未评价、证据不足、缺测、不适用和受阻分别保留。M2不能删掉未知文档后取平均。M11按公式单调性传播可用输入的上下界，界限向外舍入，不取中点或补零；无法给出可用界限时报告输入不足。记录实际运行通过、失败、仅内容核查或未验证，避免把M10内容评分写成执行成功。

### 评分规则与综合置信度

以下图示概括冻结规则；附录A列出完整五档和判定边界。这些有序档位是研究操作化约定，并不表示相邻等级具有已验证的等距含义。

**量规与权重如何形成。** 量规先从构念边界和冻结任务需求列出每项需要观察的对象，再为每项规定证据边界、缺失状态和可修复的判定条件；随后通过试跑材料和边界案例检查容易混淆的分支，冻结规则，最后用结构、引文定位和算术检查验证执行一致性。文献为“应测量什么、如何区分证据与推断、如何披露聚合假设”提供参照，但没有一篇文献直接给出本研究的五档阈值。M11在渠道内采用乘法，是为了保留发现、取得或支撑任一环节不足的限制；渠道之间采用噪声OR，是为了表达官方、第三方和模型先验可能互相补充。版本系数0.30和成本系数0.10是预先指定的工作基线，作为对主要支撑渠道的有限修正，不是从本批结果拟合出来的最优权重；敏感性分析和未校准限制因此单独报告。这样可说明分数是如何形成的，也避免把精细的数字写成已经验证的客观量表。

**官方资料（M1–M4）。** M1依据首次命中的查询和前五条结果位置评分；本次最多四次查询是实验条件，不是通用定义。M2按每个独立文档的最终获取状态评分：1为未取得可识别目标内容，2为仅标题／导航／元数据，3为明确摘要或摘录，4为直接正文但有截断或缺失证据，5为直接正文且有可核对的全文或完整目标章节起止依据。直接正文完整性未知时保留4–5区间；摘要内含代码不升级。静态页与服务端渲染页按相同内容证据判断。重试不重复计数，不同独立文档等权平均，保留原始精度；若有未知文档则报告含全部文档的均值区间。

M3按原题要求核查正文是否从概述、零散细节、完整段落发展到主流程与全部所需约束；不增加题外的穷尽要求。M4的1–5档依次为：无版本信息；有版本但无选择依据或冲突无法消解；部分适用关系明确但缺少必要对应；需自行合并有据的官方约束才能确定版本；官方已明确适用关系、直接查表或套用规则即可确定。可选版本是一个或范围均可；检索成本归M8，答案定版归M9。

![官方资料评分（M1–M4）：按发现位置、取得表示与完整性、内容详尽度及版本适用关系分别判定。](figures/figure-scoring-official-cn.svg){#fig:scoring-official description="四行1–5档。M2由未取得目标内容、仅框架、摘要摘录，递进到有缺失证据的直接正文和有完整边界依据的直接正文。M4由无版本信息，递进至无选择依据、缺少部分关系、合并官方约束、直接查表或套用规则。完整性未知保留区间。"}

**第三方资料（M5–M6）。** M5对预算内发现的相关独立第三方来源去重，0、1–2、3–4、5、至少6条对应1–5分。官方仓库和官方论坛按冻结渠道分类排除；转载和镜像不算独立来源，相关性未定时保留计数区间。M6依据关键说法的可追溯支持与矛盾判定，从存在未解决的关键矛盾，到全部关键说法有据且有独立互证。作者身份、第一手材料与可复核实验证据是可信度依据；平台名、文章新旧或转载数量不能直接换算分数。没有第三方材料时M6记不适用。

**模型自带知识（M7）。** 对检索前答案逐项核查正确性及其对原题的覆盖程度，再按最高满足档判定。自评信心仅保留为记录；不能从无检索回答倒推训练数据密度。旧记录没有检索前回答时记缺测，正确性未核清时记待定。

**检索成本（M8）。** 令$C=S+F$，其中$S$为实际搜索查询数，$F$为实际发出的获取调用数，包括失败调用。$C=1$–$2$、$3$–$4$、$5$–$6$、$7$–$8$与$C\geq9$分别得5、4、3、2、1分。预算拦截后未发出的请求不计实际获取。失败不再额外罚分；$C=0$或异常中断不自动给高分。耗时和可得token用量另存，调用数不等于完整计算成本，也不假定搜索与获取等时。

![M5–M8评分：独立来源计数、关键说法可信度、检索前知识表现与实际查询／获取成本。](figures/figure-scoring-support-cn.svg){#fig:scoring-support description="M5按0、1–2、3–4、5、至少6条来源分档。M6按关键说法支持与独立互证评分。M7核查检索前答案而非自评。M8按C等于S加F反向分档，失败调用不重复惩罚。"}

**回答产出（M9–M10）。** M9依次区分缺少所需版本、有版本但适用性无据或矛盾、部分组件有据、所有组件有据范围、所有组件有据具体版本。范围正确并不等于答案错误，但锁定粒度低于具体版本；不为提高得分臆定版本。M10依次区分仅目标描述、操作骨架、需补充或修正的具体方案、只需替换有说明的环境参数、无需补写或修正即可执行。4分不能包含内容错误修正，未上硬件运行不是4／5分的分界。两项均需最终答案引文；纯概念任务的M10或没有版本需要的M9记不适用。

![版本可锁定性（M9）与操作可执行性（M10）。](figures/figure-scoring-answers-cn.svg){#fig:scoring-answers description="M9区分版本缺失、无依据、部分组件、所有组件范围与具体版本。M10区分目标、骨架、需补改、只替换已说明的环境值与无需补改。运行状态另记，内容核查不表示执行成功。"}

**综合置信度（M11）。** 令$x_i=M_i/5$。渠道内部采用乘法，以保留各环节对该渠道支撑的限制；渠道之间采用噪声OR形式，表达任一来源可能补足其他来源的作用：

$$
OFF=x_1x_2x_3,\qquad SEC=x_5x_6,\qquad OWN=x_7,
$$

$$
K=1-(1-OFF)(1-SEC)(1-OWN),
$$

$$
M11=100K(0.7+0.3x_4)(0.9+0.1x_8).
$$

固定版本系数0.30、成本系数0.10，保留原始计算精度、展示一位小数。M11为连续百分制，不划五档，不采用$(M_i-1)/4$归一化或三渠道均值。M9/M10独立报告。该指数未经概率校准，噪声OR形式不证明渠道独立，也不允许将其解释为答对概率。

未知、不适用或受阻不能自动补零；包括M3受阻时，也不能自动令OFF=0。只有证据复核确认本轮某渠道确实无可用支撑时，才将该渠道贡献置0，并保留理由与证据；M5=1、M6不适用或某页失败本身不充分。M4预设不适用时版本因子为1，原M4仍记不适用。其余可用区间按各输入上的单调性传播：将全部下界与上界分别代入得到M11证据上下界，不表示统计置信区间。无可用界限的缺失输入仍使M11不可计算。

版本系数0.30与成本系数0.10作为预先指定的工作基线保留，不宣称最优。本轮不重新拟合系数，不把M9/M10或期望生态排序作为调整目标；先前试跑及独立系数探索不并入本批正式样本。模型选择与评价的区别、综合指标的权重假设及敏感性应披露 [@hastie2009; @oecd2008]。本次报告分项、可比任务范围与证据界限，固定公式本身不构成用途效度或概率校准证据。

排名检索评价支持固定检索深度、保留位置与相关性判断 [@manning2008]；正文抽取研究支持将正文与模板、导航分开 [@kohlschutter2010]；信息质量与API文档研究支持区分可访问性、情境相关的内容质量和任务所需细节 [@wang1996; @uddin2015; @maalej2013]。这些原则分别帮助界定M1、M2和M3/M4的对象，不提供本文的五档阈值。

第三方来源补充正式文档的研究支持检查来源互补 [@treude2016]。逐条事实核验为M6和M7的可核查陈述提供方法参照；检索上下文与最终回答分开评价则帮助保持M9/M10的边界 [@min2023factscore; @ragas2024]。M7的五档无工具任务知识表现和M10的补改程度均是本研究操作化；事实支持不能证明任务完整性或代码运行成功。交互式检索评价支持记录过程与成本，但不规定S+F及其分档，也不证明两种调用等时 [@kelly2009]。

综合指标手册支持披露聚合与权重假设及检查敏感性，不验证本研究噪声OR公式、0.30/0.10系数或指数的概率含义 [@oecd2008]。测量开发与效度文献支持明确评价领域、检查内容覆盖，并为特定解释和用途积累证据；本框架包含多个不同对象，不作为单一心理潜变量量表处理 [@boateng2018; @standards2014]。当前文献核对范围按文献账本记录，包含题录、摘要、选定章节或相关全文段落，不声称全部阅读全文。文献支持原则、日志检查通过以及多模型观察相近，均不等于具体阈值、系数或整套量规已经有效。

### 任务实施与数据分析

通过WorkBuddy CLI请求`glm-5.3`、`deepseek-v4.1-flash`与`kimi-k3-2`，显示名称分别为GLM-5.3、DeepSeek V4.1 Flash与Kimi。模型身份依据请求别名与客户端返回记录，别名不保证底层快照不可变。三模型使用WebSearch和WebFetch、同一冻结任务包和量规，每次最多4次搜索、8次获取；客户端在派发前拦截预算，最多22轮、单次采集超时600秒，生成effort为low。搜索提供方由客户端管理、未独立锁定，语言／区域、结果数量配置和temperature未暴露。这里比较的是模型与工具配置组合。

每次运行使用新的临时工作目录与会话，并设置禁用记忆的环境标志；这不是操作系统级隔离保证。三路调度交错运行任务与生态。模型在首次工具调用前输出并冻结无工具回答，随后检索并给出独立最终答案；协调子代理不属于被测模型。156次入选运行合计491次搜索、942次获取；全部有序搜索结果与实际工具返回保留。未派发的超预算请求不计调用，获取失败计一次，原始障碍和后续恢复分别记录。

后评统一由GLM-5.3完成，来源／检索前回答与最终答案分开评价。156次均完成predictors与outcome两阶段，共312份阶段结果。原始自动后评、复核后的派生评价和修订理由分层保存。技术失败允许有界重试，采用首个有效结果；仅有检索前回答而没有检索及独立终答的记录被排除。补齐两项采集和一项评分时，误触发的一次重复采集也被隔离保留，未纳入分析；没有按分数择优。

批次汇总将156份评价标为引文审计无未匹配项，149份通过结构门禁。论文整理时另对results.json中的3986条指标引文逐条回查指定原始事件（含嵌套JSON解码），3960条原文匹配，26条涉及23次运行未按原文匹配，包括省略、改写片段和协议引用；补充材料逐条标出。这项检查与批次审计标记的覆盖不同，不能将后者写成全部指标引文均已核验。本文统计复现该提交的评分与纳入规则，未据此重新评分。7份CANN记录的来源归属仍不明（GLM的J/X、DeepSeek的T/W、Kimi的A/C/T），保持未知。指定内容复核覆盖149个M10为3／4／5档的单元，以及I任务和已识别的问题；它不等于全部技术断言的专家验证。复核区分了环境值替换、需要补写内容和实际代码错误，也恢复了与冻结适用范围不符的M9判断。未进行硬件端到端执行，M10报告的是内容层面的补改需求。

M2清单覆盖实际获取返回，按独立官方文档最终状态等权聚合；同请求URL去fragment后合并重试，不把未知镜像或重定向当作同一正文。直接正文的完整性没有可核对依据时保留界限，未知归属不能静默剔除后取平均。事后取得的归属或正文参照只能用于评价，不计入当时模型上下文或检索成本。

统计先在模型内按同题两侧配对。主汇总按批次记录要求两侧均通过整份结构门禁且引文审计标记无问题，且该指标有可用点值或界限；因此一个来源归属问题也会使该运行退出其他指标的配对汇总，分母随指标变化。完整156格及排除原因仍在补充表呈现。不适用、受阻、证据不足和评分未完成不当作低分。差值定义为CUDA减CANN，界限按$[L_{CUDA}-U_{CANN},U_{CUDA}-L_{CANN}]$计算；均值界限由配对任务的上下端点分别平均，不取中点冒充确定分数。M1–M10有序评分的均值仅为描述性汇总，不假定相邻档位具有经验证的等距意义。

跨模型分析检查平均方向、逐任务反例和共同可用任务子集；每个任务仍是同一任务的不同模型观察，不能把75个潜在模型内配对当成75种独立任务，也不能用三模型替代同模型重复实验。本批全部任务属于预定分析任务，没有留出集、硬件成功率检验或重新拟合系数。结果快照、派生计算与来源定位见[本次补充材料](supplement.html)，分析基准为实验仓库提交`87e04c1`。

## 发现：用跨生态对照定位知识条件

任务级比较从开发场景、具体知识缺口和来源互补三个层面呈现知识支撑条件。以下区分跨模型重复的平均方向、具体任务的路径差异及未决证据，不把单次获取结果直接视为生态的固定属性。CANN/CUDA的差异表用于暴露诊断线索：它们描述本任务集和访问配置下的条件，不构成生态整体能力排名，也不是本文核心构念的替代物。

### 从差异到诊断：根因分类与不确定性

跨生态差异本身只是筛查信号，不能直接回答“应该改哪里”。本文把根因诊断建立在任务需求、搜索结果、获取返回形态、来源关键说法和最终答案五类证据的连接上。只有当这些证据能够排除相邻解释时，才把观察写成较具体的文档或 Agent 改进建议；否则保留为待验证假设。

| 观测组合 | 可以支持的诊断方向 | 不能直接推出的结论 | 下一步核验或改进 |
| --- | --- | --- | --- |
| M1较低，且搜索列表或官方目标未命中 | 在本次查询和预算下，官方入口的发现路径存在问题 | 不能推出官方文档不存在或生态没有相关知识 | 检查查询词、结果位置、官方索引和已知URL的直接获取 |
| M1较高，但M2为框架、摘要或正文不完整 | 入口可见，但正文交付或目标表示存在障碍 | 不能推出正文内容本身缺失，也不能仅凭长返回认定页面技术原因 | 对同一目标核对返回类型、正文边界、重试和其他官方出口 |
| M2可评而M3低于完整支撑 | 已取得的官方正文没有覆盖任务所需的步骤、参数或约束 | 不能把题目未要求的额外细节算成文档缺陷，也不能外推到整个生态 | 将缺口映射到冻结任务需求，检查是否有对应官方章节或版本分支 |
| M2/M3较高而M4较低 | 已有内容能解释操作，但缺少必要的版本—组件适用关系 | 不能推出所涉及版本一定不兼容 | 查找配套表、适用条件和冲突来源，并验证最终答案是否补入未经支持的关系 |
| M5较高而M6较低 | 第三方材料数量不等于可核验支撑，主要问题可能在来源归属、关键说法或交叉核验 | 不能把未核验直接写成错误，也不能用平台名称替代证据质量 | 逐条保留关键说法，补充独立核对和来源身份证据 |
| M7较低，但外部来源和最终答案较充分 | 本题的无检索先验不足，外部获取在一定程度上补足了它 | 不能据此推断训练数据密度或生态资料质量 | 保留检索前回答与外部证据，必要时做同模型重复或专家核验 |
| 来源关键说法有支持，但M9/M10较低 | 知识可得而回答定版或操作组织仍有问题，可能是回答合成与核验环节的缺陷 | 不能把最终答案错误归咎于文档，也不能用来源正文替代答案检查 | 对最终答案逐项回溯来源、版本条件、代码和补改清单 |
| 只有跨生态均值差异，缺少任务级证据分离 | 在当前任务组成、模型和检索条件下存在描述性差异 | 不能直接作生态整体优劣或因果归因 | 先检查同模型配对、任务范围、来源归属、预算和未知状态，再决定是否需要追加实验 |

因此，“没有找到”“没有取得”“没有识别”和“文档没有提供”在本文中不是同义词。前两者需要检索与返回日志，第三者需要来源归属和回答引用，最后一种需要在同版本、同任务范围的正文中核对缺口。模型能力、任务起点、搜索提供方、预算、页面返回和评分判断都会影响观察；本批每个模型每侧只有一次有效运行，不能把这些条件下的差异写成脱离条件的生态因果结论。对外提出修复建议时，应同时给出仍未排除的解释和下一项验证：重查同一官方目标、补做独立来源核验、进行同模型重复，或在可行时执行操作。

### 官方资料的发现、获取、内容与版本组织呈现不同缺口

官方可发现性M1的平均差在GLM、DeepSeek与Kimi中不完全同向，不能将旧的单模型搜索差异概括成稳定的全生态可见性差距。搜索词、改写和来源选择由模型产生，指标记录实际路径下的官方出现位置，不是固定查询的搜索引擎排名实验。

官方来源被找到后，实际取得的内容还可能只是框架、摘要或完整性未定的直接正文。M2按运行内独立文档聚合，不能与旧的“任务核心正文已取得比例”直接互换。两生态均须对目标文档、请求及返回表示逐项检查；没有正文只说明本次工具未取得，不足以确定SPA、robots或页面交付技术是原因。

D的CANN运行均取得了部分官方操作正文，不再是整条核心官方渠道完全不可得的案例。Kimi取得的官方资料包括编译安装命令、PyTorch打包步骤及集成说明，但Kernel/Tiling实现的关键细节仍不足；DeepSeek取得了更多工程与调用资料，但适配主体实现等仍有缺口。GLM的CUDA侧虽然M3为4，最终答案中setup.py的源文件名却与展示的文件布局不一致，M10经复核为3；其CANN侧M10为4。较详尽的来源不自动保证最终指导无需修正。对应事件与评分理由见[任务D证据](supplement.html#task-D)。

E显示错误条目与专题诊断资料所提供的支持不同。GLM取得的EZ9999条目仍以通用检查为主，但也取得故障流程和asys信息收集命令，M3为3；DeepSeek取得日志收集、`msnpureport -f`、`python3 msaicerr.py -p ... -out ...`及硬件排查相关正文，M3为4；Kimi取得错误字段解释与部分排查指引，M3为3。CUDA侧三个模型M3均为4。这支持将缺口定位到具体入口、已取得步骤及未决分支，不能声称整个CANN生态缺少具体诊断指导。[任务E证据](supplement.html#task-E)保留了原始事件引用。

A仍体现主流程支撑与局部获取障碍并存。GLM的CANN侧取得ATC转换命令、`--input_shape`、`--soc_version`和`npu-smi info`查询规则，但部分安装或参考材料只返回框架；DeepSeek通过其他官方路径取得环境配置和转换参数。不同模型没有访问完全相同的资料组合，取得其他正文也不能删除原先障碍。Kimi A-CANN的来源归属尚未确定，未纳入量化配对，但原始过程仍在补充材料保留。

检索调用的差异在三个模型中同向。相同M8配对上的平均搜索加获取次数，CANN／CUDA分别为GLM 9.74 / 8.96 (n=23)、DeepSeek 10.78 / 9.26 (n=23)、Kimi 8.95 / 6.36 (n=22)。这些是实际派发调用数，包含失败和恢复尝试；不能解释为耗时、token或完整计算成本，也不能认为调用越少必然回答越好。

版本评价揭示的是必要适用关系是否取得，而非版本数量。I的CANN侧三个模型均取得torch_npu、PyTorch和CANN的配套表，但固件驱动与CANN的具体关系仍未完整取得；CUDA侧取得多张成对关系表，却没有建立所选PyTorch wheel与实际cuDNN配套的完整依据。复核后三模型两侧M4与M9均为3。共同支持某个CUDA版本，不能自行推导PyTorch wheel与cuDNN的兼容性；有查询入口也不等于已取得关系。[任务I证据](supplement.html#task-I)将已取得表格、目标页返回和最终答案分开记录。

检索委托给Agent后，资料声明的适用条件与开发者本地事实仍是两类信息。缺少配套关系需要进一步查证来源，缺少已安装版本则需要检查环境。M9描述答案中有据定版的范围与粒度；方法型问题在未知本机环境时提供条件范围可以合理，未给唯一版本不自动等于技术错误。

### 不同来源对任务的补充作用与局限

M5的方向随模型变化：GLM的配对均值偏向CUDA，DeepSeek的界限到零，Kimi则偏向CANN。这里的数量是统一预算内实际发现、去重后的相关第三方来源，不是整个生态的社区规模。官方仓库和官方发布者不因托管于GitHub或博客平台而被算作第三方；未知归属保留未知。

第三方数量也不能直接代表可核验支撑。除7份来源归属问题外，另14份记录因M6没有可用输入而无法计算M11；这些运行中材料的取得或关键说法核验不足，不能自动将第三方渠道置零。M6的DeepSeek与Kimi平均差界限跨零，GLM的小幅差异亦应结合具体说法及共同任务分析解释。

M7改以检索前冻结回答为依据，三个模型均在CUDA侧具有较高的平均知识表现；这反映本题无工具回答的正确性与覆盖，不能倒推训练数据密度或泛化为所有开发任务的能力。M7与M9/M10评价对象不同，不能直接相减当作检索增益。来源、先验与最终回答仍需通过具体需求和证据关联。

M11的29个点值中，26个因M7=5使OWN=1，另3个因M5=M6=5使SEC=1，渠道合成K因此固定为1；26个点值来自CUDA、3个来自CANN。点值不代表所有来源分项的界限都已消除，也不能只选点值比较生态。这种渠道兜底结构解释了综合分如何形成，同时提示其不能代替单独检查正文、版本关系和最终答案。

M10经内容复核后的平均差较小；具体错误可能发生在资料已经充分的运行中，例如D的源文件名不一致，以及O的自动求导表达式错误。将最终答案检查与来源条件并列，能区分需要完善文档的任务和需要修正生成指导的任务。M11较高不等于M10较高，更不表示已在目标硬件上复现成功。

## 讨论：知识供给与 Agent 交互的设计启示

上述比较从开发场景、具体知识缺口及来源互补三个层面，形成了对生态知识支撑的认识。下面据此讨论建设重点、官方资料与Agent反馈的改进，以及社区知识与来源核验。设计示意用于具体说明其中的潜在应用，尚未评价其实施效果。

### 根据开发场景与知识需求确定建设重点

本次结果将建设重点落实到具体任务所需的知识。D、M等任务仍提示应检查实现指南、操作细节及补充案例，但场景均值的顺序随模型变化，不能据此统一排列开发场景的建设优先级。E中不同路径取得的诊断内容也不相同，应结合已取得资料和仍缺的环节确定修复对象。这体现了任务级研究的诊断价值：从开发活动及其知识需求出发，形成可核查的建设建议。

这些认识对应不同范围的改进。I中尚未取得的必要配套关系，适合通过可查询的关系组织加以处理；D中已有操作正文与仍缺的实现细节，需要分别检查内容覆盖、链接与实际交付。E则提示应将错误入口连接到已有的专题诊断资料，并补充未决分支。第三方支撑未能核验的任务还需要检查实践依据和来源归属。改进成效可以回到原任务中，检查相关知识需求是否得到更充分的支持。

### 改善官方知识供给与Agent反馈

反复出现的版本问题提示，应将适用性作为文档系统的一项属性。稳定的推荐版本入口可以与索引清晰的旧版本文档并存，每页同时声明适用版本和验证日期。驱动、工具包、框架及集成包之间的兼容关系可以通过可查询形式发布。对于 I 这类任务，开发者或 Agent 就能够针对已说明的环境请求受支持组合，减少从多个分散记录中拼接配套关系的需要。

图10 将这一建议具体化为配套查询界面。设备与框架条件限定查询范围，返回的组合同时保留来源、适用范围和验证日期；未找到有依据的匹配时，界面呈现尚未确定的条件。这使 M4 所指向的版本问题成为可检查的信息关系，也为后续确认回答的适用性提供依据。

![版本与配套查询的设计示意，依据 A、I 中需要查证的适用关系提出。选择条件、结果字段与来源检查入口展示拟议的信息组织方式；配套值为占位字段。](figures/figure-6-compatibility-design-cn.svg){#fig:compatibilitydesign description="配套查询界面示意。上方选择目标设备和框架版本；下方列出工具包、驱动范围、框架、集成包及依据等结果字段。结果仅用占位字段，保留每条关系的来源、适用范围与验证日期，未匹配时说明未知条件。设计依据为任务 A 和 I 的适用关系核查需求。"}

依赖版本的指导应将来源的适用范围与已有任务环境关联起来。在提出工具包／框架组合前，Agent可以利用任务中已提供的设备与软件事实，仅请求建立匹配所必需的其余信息。回答层指标随后检查建议是否说明适用版本条件，以及操作步骤是否明确了所需的替换或修改。

图11 以独立的环境记录说明版本核对：先区分开发者提供的本机事实与来源声明的适用范围，再将比较结果记录为匹配、不匹配或信息不足。环境记录在任务内复用，并随用户补充而更新，以支持具体命令建议前的适用性判断。

![环境声明与版本核对的设计示意，依据 A、I 的版本条件提出。设备、工具包及框架字段代表用户提供的本机事实，来源范围独立记录；图中展示信息尚不足以建立匹配的状态。](figures/figure-10-environment-design-cn.svg){#fig:environmentdesign description="上方为当前任务的设备型号、工具包、框架和集成包字段，均为占位值。下方独立呈现引用资料的版本和兼容条件，并将尚未建立环境匹配显示为需要补充信息。核对状态可为匹配、不匹配或信息不足，用户可更新同一任务中的环境记录。"}

局部获取与内容缺口需要针对任务修复。D已经取得部分官方操作正文，应先定位仍缺的Kernel、Tiling或框架适配环节，再检查相关指南是否存在、能否被发现及是否实际送达。正文交付可以采用完整HTML或同步维护的Markdown、纯文本出口，但文件形式本身不能证明任务所需内容齐全。E的错误条目可以加强与已有日志收集、AI Core错误解析及硬件排查专题的连接，并明确各工具的适用条件。对于通用兜底错误，入口应说明错误码本身不能确定什么，以及下一步需要哪些日志或本地观测。这样的页面围绕问题组织已有知识，并暴露仍需补充的诊断分支。

图12 以 E 的错误页说明任务导向内容的组织方式：从错误码能够支持的判断出发，明确需要收集的现场信息，将可观察现象关联到下一步检查和有来源的案例，并为未解决情境保留支持入口。实际填入的原因、检查步骤与案例需要由领域维护者确认；该结构帮助定位哪些知识需要补充。

Agent界面可以保留找到相关来源、取得正文和支撑某个操作步骤之间的区别。对于D，有用的状态应同时列出已取得的操作内容和仍缺的实现环节。对于E，应区分错误入口的通用说明与已取得的专题指引，说明还有哪些诊断分支需要查证或需要现场日志。对于A，可保留已有转换路径并标明局部获取障碍。这些状态将检索事件连接到当前任务的具体需求。

知识供给的改进还涉及入口与维护。稳定且可检索的官方入口影响候选资料能否被发现；明确来源归属、修订日期及兼容关系则影响后续判断。团队可以将代表性任务作为持续检查单元：跟踪查询能否命中目标资料、正文是否完整送达、版本关系是否变化，以及社区案例是否仍适用。这样的维护机制也适用于没有专门界面示例的来源治理与第三方知识供给。

针对搜索可见性的差异，文档团队可检查官方页面的搜索引擎收录情况，以及标题、摘要与开发任务用语的匹配程度，并以任务查询下的官方结果位置和发现所需轮次检验SEO改进。

### 扩充社区知识并支持来源核验

社区知识建设可以围绕任务中尚未充分获得支持的情境展开，例如具体故障案例、不同配置下的操作经验及替代实现方式。这一方向与利用Stack Overflow补充API文档的研究相呼应 [@treude2016]；本文进一步关注这些补充材料能否被Agent发现和取得，以及它们能否支撑具体任务需求。对于候选来源较少的任务，应检查缺少哪些补充说明；对于来源集中或正文无法取得的任务，应检查独立实践依据与内容交付条件。建设目标是使任务所需的经验能够被发现、取得并明确归属，而不仅是增加内容条目。

呼应人–AI交互指南中解释系统行为与支持纠错的建议 [@amershi2019]，Agent可以通过保留来源段落、适用条件及其与建议的关系，帮助开发者检查已有依据。对于仍然缺少的内容，应说明尚未获得支持的任务部分，并据此继续查找或请求必要的现场信息。来源核验与纠错反馈示意具体展示了这种信息关联方式。

由于解释可能提高建议采纳率，却未改善人机协作表现 [@bansal2021]，来源展示的效果应通过开发者能否识别缺少依据或不适用的建议来评价。

图 15 进一步示例来源核验与纠错反馈。开发者从命令展开引用段落，检查适用版本，并将实际报错或修正关联到原建议。原来源、任务环境与新增反馈共同保留，使下一轮检查能够聚焦具体分歧。这为 M9、M10 所描述的回答属性提供了可检查的依据，并支持后续修订。

![来源核验与纠错反馈的设计示意。命令与版本为说明性示例；来源展开、原文入口及关联建议的报错反馈为拟议交互。](figures/figure-11-verification-design-cn.svg){#fig:verificationdesign description="从建议展开来源与版本范围，将报错关联到原建议并保留任务上下文。命令和版本为结构示例，不作为本轮原始引文。"}

这些建议将核验建议视为编程工作的一部分，与前文讨论的信息寻找及AI辅助研究相衔接 [@brand2009; @vaithilingam2022; @barke2023]。展示每次检索事件和全部来源段落，可能增加阅读负担，却未必使下一步行动更清楚。界面可以先呈现获得支持的步骤、相关版本范围与未决条件，再按需展开来源段落。这样既优先呈现当前判断所需的信息，也保留深入检查的入口。

请求环境事实也可能打断任务，尤其是在重复询问已经提供的信息时。每次请求应说明哪项建议依赖这一事实，并复用已有任务上下文；信息可能过时时再请开发者确认。对于诊断日志，应请求相关片段，并允许移除敏感内容。缺失的配套关系和笼统的错误解释需要文档与系统团队完善，收集更多本地事实本身不能补足这些解释。如何平衡核验、打断与有效指导，仍需在这些建议的后续评价中考察。

### 诊断方法的复用

该方法将任务需求、来源或获取事件、指标编码，与判断技术建议所需信息的诊断连接起来。参与开发者平台、技术知识资源或AI Agent建设与维护的产品经理、设计师、技术写作者和开发工程师等，可据此定位缺失的指导或适用关系，并区分需要继续查找来源的情形与需要补充本地事实的情形。分析者可以沿用记录结构，并替换领域特定需求，例如数据库SDK中的客户端与服务端兼容性，或Web框架的部署前置条件。这些构成方法的预期应用方向。

后续评估可以考察独立分析者是否形成相近剖面、诊断是否与专家对缺失信息的判断一致，以及文档团队是否认为它们有助于规划修复。这些问题直接来自方法的预期用途。本次应用提供任务级区别、填写示例与跨任务综合分析，为开展此类评估奠定基础。

## 局限与研究透明度

本研究覆盖26类预定任务，各模型每侧仅保留一次有效运行；25对进入CANN/CUDA主比较，G单列。任务不是总体随机样本或独立留出集，问句起点、范围与实现层级不保证等难。三个模型提供相同协议下的交叉观察，不能替代同模型重复实验，也不能估计单元的随机运行波动。模型别名不保证固定快照，搜索提供方与部分采样参数未独立锁定，模型与工具作用相互交织。

自动后评统一由GLM-5.3完成，可能存在同模型评分偏差。原始判断与复核修订均保留，指定的M10和版本问题复核不等于全部内容的独立专家验证。引文匹配、结构门禁与算术核验分别检查证据位置、结构和计算，不证明技术正确性。补充材料另列的26条引文定位问题仍待核对，当前统计未据此改变批次纳入规则。个别归属与正文完整性判断仍未知，亦不能从工具未取得内容推断网站缺少内容或采用某种页面技术。

7份未通过来源归属门禁的记录均来自CANN，主汇总按整份运行排除；额外14份M6输入不足使M11不可计算。可比样本因此可能偏向证据较易确定的任务。共同任务子集与排除Z的描述性检查只能说明这些子集下的结果，不能消除选择偏差。M11证据界限不含运行随机性、评价者误差或未建模的不确定性；区间不是统计置信区间。噪声OR中的满值渠道可能使综合结果成为点值，即使其他输入仍有界限。固定系数、量规一致性与用途效度仍需独立评价，本轮未重新拟合系数或完成权重效度验证。

没有硬件端到端执行，不能将M10写成代码或命令复现成功率。开发者如何利用这些证据判断本地适用性，以及拟议反馈对阅读负担、任务打断和实际完成情况的影响，仍需用户研究。文献提供概念与方法依据，不直接验证本研究的五档阈值、系数或设计效果。

## 结论

本文的核心贡献是把面向AI的知识可得性定义为可检查的任务关系，并用十一项指标把知识来源、获取过程、证据支撑和最终回答连接起来。它服务于文档团队和Agent建设者：帮助他们定位资料未被发现、正文未被取得、关键任务内容缺失、版本关系不清或回答仍需补改的具体环节。CANN/CUDA案例提供了一个压力测试场景；其中的跨生态差异是诊断输出，不能脱离任务范围解释为生态整体排名。具体案例区分了取得部分操作资料但关键环节未齐、局部错误入口指导有限但可通过其他专题获得支持，以及配套关系只取得一部分等情形。

该方法使经由AI形成的技术指导的依据成为可检查的对象：哪项来源支撑拟议步骤，哪项适用关系尚未明确，以及还需要什么信息。框架、协议与案例分析提供了定位这些条件，并将其关联到知识供给和Agent反馈的方法。文档修复、继续检索和请求本地事实分别对应不同的诊断，为后续评价提供具体方向。

案例中的差异不自动等于根因；“没有找到”“没有取得”“没有识别”和“文档没有提供”必须由不同的日志和正文证据区分。本文因此把跨生态结果定位为条件化的诊断线索，并对尚未排除的任务、模型、工具和评分不确定性保留明确边界。

以下M1–M10分档与判定边界对应本批冻结rules.md及execution-checks.md；每项五档为研究约定，文献不直接验证具体档位。分项原始记录保留未评价、缺测、不适用、受阻和证据不足等状态。

**M1 官方可发现性**

1. 在预先规定的统一搜索预算内，未发现相关官方来源
2. 第三次或之后的查询才首次发现相关官方来源
3. 第二次查询才首次发现相关官方来源
4. 首次查询第2—5条出现相关官方来源
5. 首次查询第1条即为相关官方来源

本批协议每次观察前5条，最多4次查询；预算是实验条件，不是通用评分定义。查询而非调用计数，批量与并行须统一协议。首次命中后继续检索不降分，改写本身不另扣分。前序超时、列表缺失或未完成预算且未命中记待定。保存每轮全部网址与精确排名。此五档是研究约定，不是已验证量表。

**M2 官方可抓取性**

1. 未取得可识别的目标页面内容：请求失败、拒绝访问、错误页或无返回
2. 取得目标页面标题、导航或元数据，但没有可识别正文
3. 只取得明确标注为摘要或摘录的正文表示，未取得直接正文返回
4. 取得直接正文，但工具明确标注截断、缺页，或可核对的正文边界存在缺失
5. 取得直接正文，且有可核对的全文/完整目标章节起止依据，无截断或缺页证据

按每个独立官方文档的最终获取状态判定。先区分无内容、框架、摘要/摘录、直接正文，再核对直接正文是否完整。摘要中含代码不自动升级；工具自称完整提取不能独自证明完整。只有直接正文但完整性未知时保留4—5候选范围与待定，不强打4分。获取目标须在读取前明确，不能事后缩小成恰好返回的段落。复合返回如完整正文加摘要按正文证据判定；整份返回为摘要且含原文片段仍属3分。M3评内容是否详尽，M4评版本；不借答案质量判断获取状态。不同独立文档等权平均，保留原始均值；重试不重复计入，未知项不能删除后平均。

**M3 官方正文详尽度**

1. 取得的正文只有概述，没有相关解释或操作细节
2. 有相关细节，但只有零散参数、片段或说明，不能组成完整解释或操作段落
3. 有完整解释或操作段落，但完成原题所需的关键步骤、参数或约束仍缺失
4. 原题所需主流程及其参数、前提已说明，但原题明确涉及的分支、约束或参考细节未说明完整
5. 原题要求的解释、步骤、参数和约束均说明完整，无需另查才能补齐这些内容

先从原题列出需要说明的内容，禁止添加题外的穷尽要求；每项缺口附正文位置。按最高满足档判定。取不到正文记受阻，不给1分；仅导航或元数据归M2。版本选择归M4。文档内容错误另记，不能只因长而判详尽。

**M4 版本清晰度**

1. 无版本信息
2. 有版本，但无选择依据，或官方说明冲突且无法消解
3. 已明确部分适用关系，但仍缺少完成版本选择所需的对应关系
4. 需自行合并官方约束，才能确定适用版本
5. 官方已明确适用关系，直接查表或套用规则即可确定

评价对象是已取得的官方资料；无正文可评记blocked，任务无需版本选择记not_applicable。只核对原题需要的版本条件，不增加题外要求。可选版本是一个或一个范围均可，不按页面数量或版本数量扣分。合并约束必须有官方依据，不得补入未说明的假设。记录版本条件、缺失关系与冲突的原文位置。检索成本归M8，最终答案定版归M9。无法区分档位时保留区间及原因，不强行猜分。

**M5 二手丰富度**

1. 相关独立第三方来源0条
2. 相关独立第三方来源1—2条
3. 相关独立第三方来源3—4条
4. 相关独立第三方来源5条
5. 相关独立第三方来源至少6条

恢复原数量阈值，统一搜索预算内对相关来源去重计数，正文取得不是计数前提。官方仓库、官方论坛按已冻结的渠道分类排除；同一内容的转载或镜像只计一次。相关性无法确定则计数区间，区间跨档则待定。另报首次发现位置和查询数，避免声称数量单独涵盖全部可发现度。

**M6 二手可信度／一致性**

1. 存在与可靠核对依据直接矛盾的关键说法，尚未解决
2. 未发现已确证的关键矛盾，但关键说法没有可追溯的核对依据
3. 有可追溯依据支持部分关键说法，其他关键说法尚未核验
4. 全部关键说法均有可追溯依据支持，未见未解决矛盾，但缺少独立来源的交叉印证
5. 全部关键说法均有可追溯依据支持，并获独立来源交叉印证，未见未解决矛盾

关键说法限于会改变操作、解释或版本判断的可核验陈述，逐条记录支持/反驳/未知。权威性依据作者身份、第一手材料或可复核实验证据，不按平台名直接给分。转载不构成独立互证；旧文只有在内容已失效时才作为反证。没有第三方材料记N/A。此五档是证据可信程度量规，尚未校准。

**M7 模型自带知识**

1. 检索前回答没有可核验的正确任务知识，或关键主张被核对证据否定
2. 检索前仅能给出正确概念，无法给出具体方法或解释
3. 检索前能给出正确方法或解释片段，但关键细节需要外部资料补充
4. 检索前能够给出正确的完整流程或解释，原题涉及的具体参数、约束仍需补充
5. 检索前回答已准确覆盖原题所需的流程、解释、参数与约束

执行同题无工具回答并冻结，再独立核对其中知识正确性和完整性。回答前不能接触本轮检索内容；自评信心仅存记录，不用于计分。没有检索前回答的旧运行记缺测。该测量只能反映无检索知识表现，不能推断训练数据覆盖密度；未知正确性则待定。

1. C≥9
2. C=7—8
3. C=5—6
4. C=3—4
5. C=1—2

**M9 版本可锁定性**

1. 最终答案未提供原题需要的版本信息
2. 提到版本，但没有给出有依据的适用版本或范围，或关键定版与证据矛盾
